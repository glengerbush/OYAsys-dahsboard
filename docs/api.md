# OYAsys browser contract

Telemetry times are Unix milliseconds; software-update `checked_at` is Unix seconds. All API responses are JSON. Prefix: `/api/v1`. Requests must use the configured public origin’s Host; supplied Origin headers must match it exactly. There is no CORS access.

`GET /state` returns `{ inventory, snapshot, settings, csrf_token, storage, now_ms }`.
`inventory`: `{ hostname, system: [{label,value}], metrics: [{id,label,unit,group,source}], warnings: [string], synthetic: boolean, availability?: {metric_id:{status,reason?:string}} }`. Current availability is `available`, `warming_up`, `unsupported`, `permission_denied`, `lost`, `unavailable`, or `invalid`; reasons expose capability/read failures. It is transient, excluded from persisted catalog identity, and absent in older fixtures. Numeric zero remains valid regardless of display status.
`inventory.drives` optionally lists cached whole physical devices as `[{id,name,model,capacity_bytes:number|null}]`; `id` is the prefix for that device’s `.read` and `.write` metrics. An omitted list means no physical devices were discovered. Capacity is hardware size, not filesystem free space.

Groups: `gpu`, `cpu`, `memory`, `thermal`, `fan`, `storage`, `network`, `system`. Units: `°C`, `RPM`, `%`, `bytes`, `bytes/s`, `W`, `MHz`, `s`.
Metric IDs identify devices, never enumeration order. A P100 temperature metric has group gpu and ID ending `.temperature`; its source contains P100's identity. Other GPU IDs end `.utilization`, `.memory_used`, `.memory_total`, `.power`, `.clock`.
`snapshot`: null before first collection, else `{ sequence, timestamp_ms, values: { metric_id: number|null }, persisted: boolean }`. Null means unavailable, never zero. Numeric metrics are display gauges; exact raw counters stay internal to telemetry.
`settings`: `{ revision, sampling_seconds, retention_days, p100_fan_id: string|null }`. Defaults 0, 10, 30, null. Selecting a fan is the operator's verification of its physical mapping.
`storage`: `{ available, error: string|null, bytes, samples, oldest_ms: number|null, newest_ms: number|null, estimated_daily_bytes: number|null }`. Statistics refresh during maintenance (normally every 30 seconds). Bytes include database and WAL. The daily estimate extrapolates observed occupied SQLite pages over retained coverage; fixed schema/catalog overhead makes short-window estimates conservative. Null means insufficient coverage.

`PUT /settings`: same settings object plus `confirm_delete: boolean`. Requires exact configured Origin and `X-OYAsys-CSRF` from state. JSON only; body at most 4096 bytes. Success returns effective settings; stale revision 409; invalid input 400; shorter retention without confirmation 409; storage failure 503. Interval 1..3600 seconds, retention 1..365 days. A new fan ID must be a discovered RPM metric or null; an unchanged saved mapping remains valid while its source is absent. Unknown fields rejected. Expiration has a durable monotonic cutoff, so increasing retention cannot restore previously expired readings.

`GET /history?from=<ms>&to=<ms>&metrics=<comma-separated-URL-encoded-ids>&points=<n>` returns `{from_ms,to_ms,reduced,series:[{id,points:[[timestamp_ms,number|null],...]}],coverage:{oldest_ms,newest_ms},next_after:null}`. Points budget is per series (minimum 8, maximum 2000), max 64 selected metrics. Selected range max 365 days. Reduction preserves extrema, temporal order, and gaps. Missing/invalid fields 400; historical worker busy 429; unavailable storage 503. Work/representation limits return 422 with a narrower-range recommendation: at most 3,200,000 scanned collections, eight seconds of scan work, and enough display points to preserve gap boundaries. No silent truncation. Coverage describes actual retained history. History/updates replies return 409 if settings changed while work was queued or running; reload state and retry to avoid displaying a result from an obsolete retention window.

`GET /updates?after=<sequence>&limit=<n>` returns `{snapshots:[snapshot,...],next_after,reset_required,settings_revision,state}`. Limit 1..1000 snapshots (default 100), additionally capped at 8192 metric values across returned snapshots. A wide catalog can therefore return fewer snapshots than requested; continue from `next_after`, or reload a bounded chart range when it precedes the current snapshot sequence. Snapshots before current retention cutoff never returned. If after precedes retained coverage or server sequence history is incompatible, reset_required is true; browser reloads a bounded range. `state` has the same complete shape as `GET /state`, allowing one request per live refresh. This endpoint supplies missed collections, not new hardware reads. `GET /health` returns `{status: "ok"|"degraded", storage, last_collection_ms, now_ms}`.

`POST /refresh` explicitly rediscovers inventory on the collector thread and returns the updated inventory. Requires exact configured Origin and `X-OYAsys-CSRF`; no request body is required. It does not change cooling controls. A busy collector returns 429, a failed/timed-out refresh 503.

## Software updates

`GET /software-update` returns `{enabled,current_version,state,latest_version,message,checked_at,request_id}`. `latest_version`, `checked_at`, and `request_id` may be null when unknown; `current_version` always identifies the running binary. States: `disabled`, `idle`, `checking`, `available`, `current`, `installing`, `updated`, `rolled_back`, or `error`. This reads bounded local status only; it never checks GitHub. `GET /health` also includes `version` for startup verification.

`POST /software-update/check` requests an explicit release check. `POST /software-update/install` requires JSON `{version:"X.Y.Z"}`, matching the newer available version from the prior check. Both require exact Origin and `X-OYAsys-CSRF`. Accepted work returns 202 with status; busy/stale/unavailable version returns 409; a disabled or broken installation returns 503; malformed input returns 400. Install bodies are bounded to 4096 bytes and unknown fields are rejected. No browser-provided URL, path, repository, or command is accepted.

`OYASYS_UPDATER_DIR` enables the filesystem bridge for installed services; local previews omit it and report `disabled`. The HTTP process reserves each operation through an atomic inbox receipt before publishing its request. Pending work survives browser closure and application restarts, blocks duplicate requests, and must match the worker's terminal request identity before being cleared. Stale/ambiguous operations fail closed instead of automatically retrying an installation. See [update operations](updates.md) for service setup and recovery.

Settings mutations return 409 during a pending installation or unresolved recovery journal. The guard also runs before the collector persists a queued settings command. A candidate service may serve live readings before the updater confirms health; it cannot acknowledge settings changes that a subsequent rollback would erase.

The UI reads status when Settings opens, then only polls local status while an operation is active and both Settings and the document are visible. Release checks always require a click. Successful updates reload embedded assets and obtain a fresh CSRF token from the restarted process. No update state is included in routine telemetry responses.

Dashboard loads state initially, then polls updates at sampling cadence only while visible; a full range query occurs on initial load or range/metric change. Assets are embedded in the same executable: fingerprinted URLs, build-time gzip, ETags, immutable fingerprint caching, and conditional 304 responses. Original asset names remain aliases. UI never expects specific physical devices to exist.

Test interface: executable `serve --bind 127.0.0.1:PORT --origin http://127.0.0.1:PORT --data-dir DIR --fixture FIXTURE`. Fixture is JSON `{inventory, samples:[{timestamp_ms,values}], now_ms?}`; deterministic fixture samples import once on startup only if storage is new and empty; a persisted marker prevents reimport after retention deletes everything. Fixture mode is explicitly synthetic and never a default. Normal behavior is asserted through HTTP; fault tests also manipulate disposable SQLite versions and process limits, and verify foreign-schema preservation. Optional `--fixture-clock FILE` reads integer Unix ms for deterministic retention/scheduler tests; accepted only with `--fixture`. Without a clock file, `now_ms` anchors a clock that advances with process elapsed time. Fixtures are for qualification, not production telemetry.

`oyasys discover` prints inventory JSON with an additional `readings` map containing one current sample. Missing/unsupported readings are null; rate readings require a second sample and may initially be null. The command performs read-only discovery and does not create a database.

The executable holds a nonblocking advisory lock on `oyasys.lock` inside an available data directory. A second instance using that directory exits before serving. If storage is unavailable, live monitoring remains available; recovery must acquire the same lock before opening history. Keep the lock file in place during operation.

## Folder analysis

`POST /storage/analyze` takes `{ "metric_id": "filesystem.<id>.total" }`. Requires exact configured Origin, `X-OYAsys-CSRF`, and JSON (4096-byte maximum); unknown fields are rejected. The mount is resolved from discovered filesystem inventory, never a caller-supplied path. An unavailable filesystem or concurrent scan returns 409, invalid selection 400, and launch/worker failure 503.

Success returns `{ entries: [{name,bytes}], total_bytes: number|null, files_bytes: number|null, other_folders_bytes: number, complete: boolean, message: string }`. Entries are the largest 12 immediate folders by allocated bytes. Other folders are aggregated; files_bytes includes direct files and root directory metadata. A missing completed root total is null. Partial results return 200 with `complete=false`; these must not be displayed as a complete accounting of used disk space. Results are not persisted. See [scan limits and permissions](architecture.md#filesystem-capacity-and-folder-analysis).
